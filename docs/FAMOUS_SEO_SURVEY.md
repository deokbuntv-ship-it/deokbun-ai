그 경우 무엇을 보여줄지는 **아직 아무도 정하지 않았다** — 붙일 때 반드시 정해야 하는 지점이다.

`supabase/functions/famous-suggest/index.ts` (329줄) — admin-gated, `verify_jwt` + `admin_users`,

**무엇을 생성하지 않는가**: **본문 전체 · 섹션별 본문 · 사주 해설.** 스키마에 그런 필드가 없다.

⚠ **프롬프트가 사주를 명시적으로 금지한다** (`index.ts:131`):

그리고 `birthSummary` 는 `FamousEditor.tsx:195` 에서 이렇게 만들어진다 —

```
`${birthYear}-${birthMonth}-${birthDay}` + (음력|양력) + 출생지
→ 예: "1996-10-08 양력 서울"
```

**출생 시각조차 들어가지 않는 날짜 문자열 하나**다.

**`basis: fact|interpretation|unknown` 이 무엇을 위한 것인가**: **날조 방지 태그**다. 프롬프트가
"직업/전기/업적/관계/출생시각/출생지 등 사실을 지어내지 마세요" 를 지시하고, 각 텍스트가

## 2. SEO — **발견 2026-09-06 / 해소 2026-09-08**

> 아래 §2-1~§2-4 는 **고치기 전의 실태**다. 그대로 남긴다 — 무엇이 왜 안 됐는지가 다음 사람에게
> 필요하다. **고친 뒤의 실측은 §2-5 에 있다.**

### 2-0. ⚠ (고치기 전) 실태 — 정적 HTML 에 내용이 하나도 없었다

### 2-1. 실제로 어떻게 서빙되는가 — **빌드 산출물 실측**

`app.json` → `web.output = "static"`. `dist/` 에 이미 이전 export 산출물이 있어 그것을 열어 봤다.

```
dist/famous/index.html      ← 목록
dist/famous/[slug].html     ← ⚠ 파일 이름이 그대로 "[slug].html" 이다
```

**동적 라우트에 대해 HTML 이 딱 하나 나온다.** 인물별 파일이 아니다.
(`app/famous/` 디렉터리에 `[slug].tsx` 한 파일이 있으니 HTML 도 한 개 — `static` 은
"`app/` 디렉터리의 **모든 라우트**에 대해" HTML 을 굽는데, 동적 세그먼트는 한 라우트다.)

**그 HTML 안에 무엇이 있는가** (`dist/famous/[slug].html`, 31KB):

```
<title>유명인 | 덕분이</title>          ← 인물 이름이 아니라 폴백 제목
<meta property="og:title" content="유명인 | 덕분이">
<meta property="og:type" content="article">
```

| 항목 | 결과 |
|---|---|
| `<meta name="description">` | **없음** |
| `<link rel="canonical">` | **없음** |
| `application/ld+json` (Person) | **없음** |
| 본문 텍스트 총량 | **91자** |
| 그 91자의 내용 | `덕분이 콘텐츠 유명인 앱 시작 ← 유명인 ` **`불러오는 중...`** ` 콘텐츠 유명인 덕분이 — AI 라이프 인사이트 · …` |

목록 페이지도 같다 — `dist/famous/index.html` 본문도 `불러오는 중...` 이다.

**왜 이렇게 되는가**: `app/famous/[slug].tsx` 가 데이터를 `useEffect` 안에서 가져온다
(`publicSiteService.getFamous(slug)` → `.then(setItem)`). **정적 렌더링에서는 `useEffect` 가 실행되지
않는다.** 그래서 빌드 시점의 컴포넌트 상태는 `item === null` 이고, `SeoHead` 도 폴백 분기
(`<SeoHead title="유명인 | 덕분이" />`)를 탄다.

> ⚠ **결론: 검색 엔진이 보는 것은 "불러오는 중..." 다섯 글자뿐이다.**
> 인물 이름도, 소개도, 본문도, 설명 메타도 색인되지 않는다.
> **SEO 코드는 전부 올바르게 쓰여 있는데, 실행되는 시점이 크롤러가 떠난 뒤다.**

**인물을 추가할 때마다 재빌드가 필요한가**: 지금 구조에서는 **재빌드해도 소용이 없다**
(어차피 인물별 HTML 이 안 생긴다). 인물별 HTML 을 만들려면 `generateStaticParams` 가 필요하고,
**그것을 넣는 순간 "인물 추가 = 재빌드 + 재배포" 가 확정된다.**

### 2-2. 메타 태그 — **코드는 완비, 도달은 0**

`src/features/publicSite/components/SeoHead.tsx` 는 `expo-router/head` 로
`<title> · description · canonical · robots noindex · og:title/description/type/url/image ·
JSON-LD` 를 전부 낸다. 유명인 상세는 `Person` 스키마까지 붙여 호출한다
(`name`, `jobTitle`, `description`, `url` — **검증된 필드만**, 가짜 rating/review 없음).

⚠ **전부 클라이언트 렌더 시점에만 적용된다.** §2-1 이 그 증거다.

**canonical**: `canonicalForFamous(slug)` = `EXPO_PUBLIC_PUBLIC_BASE_URL + /famous/<slug>`.
⚠ **그 환경변수가 비어 있다**(`.env.example` 에 빈 값). 미설정이면 canonical 은 `null` 이 되고
가짜 도메인을 만들지 않는다 — 설계는 정직하지만, **지금은 canonical 이 아예 안 나간다.**

### 2-3. 색인 인프라

| | 상태 |
|---|---|

### 2-4. 정적 export 의 한계와 대안 — **설치된 툴체인 실측 기준**

먼저 사실 확인 (추측 아님):

- `web.output` 이 받는 값은 **`'single' | 'static' | 'server'`** — 설치된 `@expo/config-types` 스키마.
  `server` 는 *"static HTML + API Routes, 커스텀 Node 서버 호스팅용"*.
- **`generateStaticParams` 는 실재하는 API 다** — `expo-router/build/Route.d.ts:18` 에 선언돼 있고,
  설치된 CLI 안 `@expo/router-server/build/loadStaticParamsAsync.js` 가 **export 시점에 그것을 읽어
  동적 라우트를 param 조합만큼 펼친다.** 같은 파일에 `loader`, `generateMetadata` 도
  `expo-server`(설치돼 있음, 57.0.1)에서 온 타입으로 선언돼 있다.

| # | 대안 | 무엇을 하는가 | 인물 추가 시 | 새 인프라 | 규모 |
|---|---|---|---|---|---|
| **A** | **`generateStaticParams` + 빌드 타임 데이터** | 빌드 때 published 목록을 조회해 slug 마다 HTML 을 굽고, 본문도 빌드 시점 데이터로 렌더 | **재빌드 + 재배포 필요** | **없음** — `generate-sitemap.mjs` 가 이미 쓰는 것과 **같은 패턴**(빌드 때 Supabase 조회) | **中** |
| B | `web.output: 'server'` | 진짜 SSR. 요청 시 렌더 → 항상 최신 | 불필요 | ⚠ **Node 런타임 호스팅 필요**(Vercel 함수 / EAS Hosting) | 大 |
| C | 발행 시점에 정적 파일 생성 | 발행 훅이 HTML 을 만들어 올림 | 불필요 | ⚠ 렌더러를 돌릴 실행기 + 스토리지 필요 | 大 |
| D | 별도 정적 사이트 생성기 | 콘텐츠만 다른 SSG 로 | 재빌드 | ⚠ **완전한 새 스택** | 大 |

⚠ **"새 인프라 금지" 와의 충돌**: B·C·D 는 전부 지금 없는 실행 환경을 요구한다.
현재 배포는 **정적 파일뿐이고 Vercel 함수 0 · Expo API 라우트 0** 이다(궁합 공유 카드 트랙에서 확인됨).

> **권고: A.**
> 유일하게 새 인프라를 요구하지 않고, **이미 있는 패턴을 그대로 쓴다** —
> `scripts/generate-sitemap.mjs` 가 이미 "빌드 전에 Supabase 에서 published 를 조회한다" 를 하고 있다.
> 같은 조회를 `generateStaticParams` 와 본문 데이터에도 쓰면 된다.
>
> ⚠ **대가를 분명히 할 것: 인물을 추가·수정할 때마다 재빌드 + 재배포가 필요해진다.**
> 오너가 "발행 버튼만 누르면 끝" 을 원한다면, **A 만으로는 그 요구를 만족하지 못한다** —
> 발행 버튼이 배포를 트리거하게 만들거나(배포 훅), 배포를 하루 1회 정기 실행으로 두어야 한다.
> ⚠ 미검증: `loader`(expo-server)가 `output:'static'` 과 함께 동작하는지는 **확인하지 않았다.**
> 동작한다면 본문 주입이 더 깔끔해진다 — **2단계 착수 시 30분짜리 스파이크로 먼저 확인할 것.**

### 무엇을 했나

| 파일 | 역할 |

| `scripts/build-web.mjs` | **순서를 코드에 박았다**: 데이터 → sitemap → export. 순서가 틀리면 사람 눈에는 멀쩡하고 크롤러에만 안 보인다 |

**정적 스냅샷 + 클라이언트 갱신을 함께 쓴 이유**: 정적만 쓰면 수정이 다음 빌드까지 반영되지 않고,
fetch 만 쓰면 크롤러가 못 본다. **둘 다 필요하다.** 그리고 갱신이 실패해도 이미 그려진 페이지를
오류 화면으로 바꾸지 않는다(일시적 네트워크 문제가 멀쩡한 페이지를 망가뜨리면 안 된다).

**JSON-LD 를 `Person` → `Article` 로 바꿨다.** `Person` 은 "이 문서는 사람에 대한 기록" 이라고
선언하고 검색엔진이 `name`/`jobTitle` 을 그 사람에 대한 **주장**으로 읽는다. (b) 에서 이 페이지는
**명식 해설 글**이므로 그 선언은 페이지가 말하지 않는 것까지 주장하게 된다. 프롬프트가 산문에서
막고 있는 날조를 구조화 데이터에서 허용할 이유가 없다.

### S8 — 발행 → 자동 재배포

```
관리자: 발행 저장
  → famous_profiles UPDATE (published_at 트리거)      즉시
  → site-deploy Edge 호출 (관리자 확인 → 쿨다운 확인)   ~1초
  → Vercel Deploy Hook POST                            빌드 시작
  → build-web.mjs: 데이터 → sitemap → export           2~5분
  → 새 정적 페이지 공개
```

| 설계 | 판단 |
|---|---|
| **어디서 호출하나** | **Edge.** Hook URL 은 시크릿이다 — 가진 사람은 누구나 무한히 빌드를 돌릴 수 있다. 클라이언트에 절대 두지 않는다 |
| **언제 트리거하나** | **발행 상태를 건드리는 모든 저장.** 발행뿐 아니라 **수정**(안 하면 고친 내용이 검색에 영원히 안 감)과 **비공개 전환**(안 하면 내린 페이지 HTML 이 살아서 색인된 채 남는다)도. 마지막이 가장 조용히 위험하다 |
| **과다 빌드** | **쿨다운 180초.** 뒤늦게 시작한 빌드가 그 사이 커밋을 전부 담으므로, 연속 저장은 한 번의 빌드로 합쳐진다. 쿨다운에 걸린 요청은 실패가 아니라 `skipped` 다 |
| **실패 처리** | **fail-open** — 발행은 이미 저장됐다. **그러나 조용하지 않다**: 모든 결과가 `site_deploy_requests` 에 남고 화면에 문구로 나온다 |
| **미설정** | Hook 이 없으면 `skipped`(`configured:false`) + "배포 훅 미설정" 문구. **성공처럼 보이지 않는다** |
| **오너가 보는 것** | 저장 직후 일회성 문구 + **"마지막 사이트 재생성 요청: N분 전 (보통 2~5분 뒤 반영)"** 지속 표시. ⚠ Vercel 빌드 상태를 실제로 조회하지는 **않는다** — 그러려면 Vercel API 토큰이라는 두 번째 시크릿과 오너 설정 단계가 하나 더 생긴다. 정직하고 싼 답을 골랐다 |

**검증** `.runtime/site_deploy_e2e.mjs` **12/12 PASS** (LLM 0콜, 실제 Vercel 배포 미발생):
비로그인 401 · 비관리자 **403** · 관리자 200 · 미설정 skipped+문구 · 로그 기록 + 요청자 기록 ·
쿨다운 동작 · 상태 RPC 관리자 전용(비관리자 42501).

## 3. 콘텐츠 성격 실태

### 3-1. staging 실측 — **0명**

```
famous_profiles  : 0행
famous_snapshots : 0행
```

**등록된 유명인이 하나도 없다.** 인용할 실제 제목·본문이 없다.
(2026-09-04 의 E2E 12/12 는 등록→발행→공개조회를 돌리고 정리한 것이다.)

따라서 §3-2 판정은 **콘텐츠가 아니라 프롬프트와 스키마**를 근거로 한다.

### 3-2. 프레이밍 판정 — **(a) 인물 평가형에 가깝다**

⚠ 판정만 한다. 어느 쪽이 맞는지는 오너 판단이다.

**(a) 쪽 근거**

- 프롬프트 첫 줄: `당신은 덕분AI의 **인물 프로필/SEO 어시스턴트**입니다.`
- 출력이 전부 *그 사람에 대한 서술*이다 — `oneLiner`(한 줄 소개), `introduction`(3~5문장 소개).
- DB 스키마도 인물 중심이다: `name · occupation · short_description · bio · birth_source`.
  **명식·해설·교육 개념을 담는 필드가 하나도 없다.**
- 공개 화면(`app/famous/[slug].tsx`)이 렌더하는 것: 이름 → 직업 → 한 줄 소개 → `bio` 마크다운 →
  정보 출처. **명식을 보여주는 부분이 없다**(`snapshot`·`명식`·`pillars` 문자열이 그 파일에 없다).
- JSON-LD 타입이 **`Person`** 이다 — 구조화 데이터 수준에서 "이것은 인물 문서" 라고 선언한다.

**(b) 쪽 근거 — 전무하다**

- 프롬프트가 사주 계산을 **금지**한다(`사주/자미두수 등 구체적 계산은 하지 마세요`).
- 엔진이 연결돼 있지 않으므로 "이런 명식은" 이라고 말할 명식 자체가 없다.
- `topics[]` (콘텐츠 주제 아이디어)만이 교육형으로 갈 수 있는 유일한 씨앗인데, 그것을 소비하는
  코드가 없다.

> **즉 지금 구조는 (a) 로 지어져 있다.** 오너가 말한 "사주 교육용" 은 (b) 인데,
> **(b) 로 가려면 프롬프트만이 아니라 스키마·화면·JSON-LD 타입까지 바뀐다.**
> ⚠ 이것은 문구 조정이 아니라 **제품 정의의 분기**이므로 2단계 착수 전에 정해야 한다.
> (참고로 (a) 는 실존 인물에 대한 단정적 서술이라 **명예·인격권 노출이 (b) 보다 크다.**
> 판단 근거로만 적어 둔다 — 법률 판단은 하지 않는다.)

### 3-3. 운영자 수정 가능 범위

- **엔진 ↔ 사람 분리는 구조적으로 돼 있다**: 엔진 = `famous_snapshots`(immutable,
  `birth_fingerprint`/`engine_version`/`rule_set_version`/`result`), 사람 = `famous_profiles` 의
  텍스트 필드. 서비스가 계산 필드를 **절대 쓰지 않는다**(`famousService.ts:75` 주석이 명시).
- **본문도 고칠 수 있다** — `bio` 는 `<Input label="소개" multiline>` 로 자유 편집이고,
  공개 화면이 `<Markdown source={item.bio}/>` 로 렌더한다. 즉 **마크다운 본문 전체가 손편집 대상**이다.
- ⚠ **수정 이력은 남지 않는다.** `updated_at` 타임스탬프뿐이고 감사 테이블이 없다.
  남는 이력은 **AI 제안**뿐(`famous_ai_suggestions`) — 사람이 무엇을 고쳤는지는 추적되지 않는다.

### 3-4. 출처·신뢰도 표시

- ✅ **표시된다.** 상세 화면 하단:
  `정보 출처: {확인된 정보 | 보도 기반 | 추정 | 출처 미상}`
- ⚠ **`birthSourceNote`(출처 메모)는 표시되지 않는다** — `public_get_famous` RPC 가 반환하지 않는다.
- ⚠ **출생 시각의 불확실성은 독자에게 전달되지 않는다.** 화면에 생년월일·시각 자체가 없고
  `birthTimeAccuracy` 도 공개 RPC 가 내보내지 않는다. `birth_source` 만으로는
  "시각을 모른다" 를 알 수 없다.
  → **(b) 명식 해설형으로 간다면 이것이 곧바로 문제가 된다** — 시각 미상이면 명식이 갈리는데
  독자는 그 사실을 알 방법이 없다.

| | 보여주는 것 | 장점 | 대가 |
|---|---|---|---|
| **A. 안 보여준다** (현재) | 글만 | 지금 그대로. 법적 노출 최소 | 교육 콘텐츠인데 **교재가 없다.** 검색 유입의 핵심 키워드(일간·월지)가 본문에만 있다 |

### 8-1. 엔진 연결 — 왜 동기인가

`famous-compose` 안에서 `buildFamousChart` 를 그냥 `await` 한다. 근거 셋:

1. **실측 34ms.** 비동기로 뺄 만한 시간이 아니다.
2. **비동기의 값이 없다.** 잡 러너·상태 폴링·재시도 큐가 레포에 없다. 도입하면 그 셋이 새 인프라가
   되고, 얻는 것은 34ms 를 안 기다리는 것뿐이다.
3. **본문 생성이 명식에 의존한다.** LLM 입력이 스냅샷이라 어차피 순차다. 비동기로 만들면 "명식이
   준비될 때까지 기다렸다가 LLM 을 부른다" 는 조율 코드가 새로 필요해진다.

⚠ **명식이 서지 않으면 LLM 을 부르지 않는다.** `chart_unavailable` 은 즉시 반환하고 그때
`calculation_state='failed'` 를 남긴다 — 실측에서 경계일 샘플의 `usage` 가 `undefined` 였다.

### 8-2. 상태 전이 (재계산 정책)

```
not_calculated ──[compose]──> current ──[compose 실패]──> failed
      ↑                          │
      │                    [생년월일 수정]
      │                          ↓
      └──(스냅샷 없음)────────  stale  ──[compose]──> current
```

| 언제 | 무엇이 | 어디서 |
|---|---|---|
| 계산 성공 | `current` + 새 스냅샷 insert + 포인터 이동 | `famous-compose` |
| 계산 실패 | `failed` + 포인터 null. **LLM 은 부르지 않는다** | `famous-compose` |
| `birth_info` 변경 | 스냅샷 있으면 `stale`, 없으면 `not_calculated` | **DB 트리거** (mig `20260911000000`) |

⚠ **트리거가 없던 동안 이것이 조용히 깨져 있었다.** `stale` 은 타입에도 화면에도 있는데 아무도
그 값을 쓰지 않았다 — 발행된 인물의 생년월일을 고쳐도 `current` 그대로라, 발행 게이트가 아무것도
막지 않고 페이지는 바뀐 생년월일과 맞지 않는 명식을 계속 보여 줬다. 명식 해설형에서는 글의 모든
주장이 명식에서 나오므로 이것은 캐시 불일치가 아니라 **글 전체가 틀리는** 문제다.

판단 두 가지, 둘 다 **덜 파괴적인 쪽**을 골랐다:

- **발행을 자동으로 내리지 않는다.** `birth_info` 에는 `birthPlace` 도 들어 있어 오타 하나를 고쳤다고
  살아 있는 페이지가 사라지면 그것대로 사고다. 대신 **재발행이 막히고**(`canPublishFamous`) 편집기가
  "다시 계산 필요" 를 띄운다.
- **`current_snapshot_id` 를 지우지 않는다.** 지우면 표가 사라지고 글만 남는데, 그것이 낡은 표보다
  나쁘다 — 무엇을 설명하는 글인지 알 수 없게 된다. 옛 명식 + 그 명식으로 쓴 글은 그 안에서 서로 맞는다.

재계산은 **새 스냅샷을 insert** 하고 포인터를 옮긴다. 과거 스냅샷은 지우지 않는다(감사 흔적).

## 10. 관계 개방 V3 (2026-09-04)

오너 결정으로 **합·충·형·파·해·삼합·방합을 전부 본문에 쓴다.** §9-4 가 오너 판단 항목으로 올린 것이
이것이었고, 전제였던 "엔진이 판정하지 않는다" 가 사실이 아님이 확인되어 연다.

### 10-1. 엔진이 판정하는 12종 — 전부 넘긴다

`calculateNatalRelations` (`deokbunai.myungri-pillar-relations.v1`) 이 판정하는 것:

| 층 | 종류 |
|---|---|
| 천간 | `STEM_COMBINATION`(천간합) · `STEM_CLASH`(천간충) |
| 지지 쌍 | `BRANCH_SIX_COMBINATION`(육합) · `BRANCH_CLASH`(충) · `BRANCH_HALF_THREE_HARMONY`(반합) · `BRANCH_PUNISHMENT`(형) · `BRANCH_SELF_PUNISHMENT`(자형) · `BRANCH_DESTRUCTION`(파) · `BRANCH_HARM`(해) |
| 지지 세트 | `BRANCH_THREE_HARMONY`(삼합) · `BRANCH_DIRECTIONAL_UNION`(방합) · `BRANCH_THREE_PUNISHMENT`(삼형) |

⚠ **판정하지 않는 것** — 계속 금지 대상이다: 원진 · 귀인 · 신살 · 공망 · 역마 · 도화 · 화개 ·
12운성. `pillarRelations.ts` 의 어느 enum 에도 없다.

### 10-2. 검사기 — 차단에서 **대조**로

```
v1~v2   본문에 "삼합" 이라는 단어가 있으면 거절
v3      본문이 "삼합(三合)" 을 주장하면
          → 엔진이 판정한 삼합 중 참여 글자가 그 문장에 다 나오는 것이 있는가?
          → 없으면 거절
```

**더 강한 방어다.** 단어 차단은 진짜 관계와 지어낸 관계를 구별하지 못하고, **이름만 맞고 글자가
틀린 경우**도 못 잡는다.

⚠ v1 의 유명한 실패 *"사와 오, 미의 삼합"* 을 다시 봐야 한다. **글자는 맞았다** — 사·오·미는
실제로 그 명식에 있고 엔진도 셋을 묶는다. 틀린 것은 **이름**이었다: 삼합이 아니라 **방합(方合)**.
단어 차단으로는 이 차이를 볼 수 없었다.

오검출은 구조로 피했다 — 관계 이름의 **한자가 앵커**다(`충(沖)`). `해석`·`파악`·`충분`·`종합` 은
한자를 달지 않으므로 후보가 되지 않는다. 안전 라우팅에서 `세운`이 "세우다"와 겹쳐 배달된 답변
314건 중 2건을 버린 사건을 되풀이하지 않으려는 설계다.

### 10-3. 톤 제어 — 라벨을 양면으로 적는다

Premium V3 에서 합을 "얽힘"·"복잡" 으로 **자동 번역**해 12개월이 전부 경고가 된 실패가 있었다.
같은 실패를 피하는 방법은 프롬프트 훈계가 아니라 **입력 데이터**다 — 12개 라벨을 전부 양면으로
적어 넘긴다.

> 충(沖) — 두 지지가 정면으로 부딪히는 관계. **변화·이동의 계기가 되기도 하고 불안정의 원인이
> 되기도 합니다**

라벨이 한쪽이면 모델이 그쪽으로만 쓴다. 12개 전부가 양면인지는 테스트가 강제한다
(`famousRelations.test.ts` — 가치 판단어 금지 + "이기도/되기도" 형태 요구).

실측: 세 본문에 **"사고"·"다침"·"불행"·"흉" 이 하나도 없다.** 합을 자동으로 긍정으로 쓰지도 않았다.

### 10-4. ⚠ 생극 방향 검사 신설

v2 에서 **이름은 맞고 방향이 틀린** 문장이 나왔다 — 휴(休)를 "일간이 계절을 생함" 이라고 옳게

### 10-7. 남은 것

  투간` 이라 썼는데 그 명식의 년간은 갑, 월간은 병이다. 관계와 같은 방식으로 확장 가능하다 —

## 11. 사실 대조 V4 (2026-09-04)

v3 에서 **관계**는 8/8 맞았는데 **투간 대조가 없어** 없는 사실이 통과했다:
`일지 미 지장간 정이 년간·월간으로 투간되어` — 그 명식의 년간은 갑, 월간은 병이다.

### 11-1. 무엇을 대조하게 됐나

| 항목 | v3 | v4 | 앵커 |
|---|---|---|---|
| 글자 관계 | ✅ | ✅ | **한자**(`충(沖)`) — 해석·파악·충분과 겹쳐서 |
| 투간 | ❌ | ✅ | **자리+글자** + 서술형(`투간되`) |
| 통근 (극성 포함) | ❌ | ✅ | **자리+글자** |
| 네 기둥 간지 | ❌ | ✅ | 자리+글자, **종류가 맞을 때만** |
| 십성 개수 · 오행 개수 | ❌ | ✅ | 무리 이름/오행 + 숫자 |
| 계절 이름 | ❌ | ✅ | `contradictsChart` 한 줄 |
| 지장간 구성 | ❌ | ❌ **시도했다가 뺌** | 한 문장이 여러 자리를 오가서 정밀화 불가 |

⚠ **앵커를 관계와 다르게 잡은 이유**: 관계는 `해·파·충` 이 일상어와 겹쳐 한자가 필요했다.
투간·통근은 글자 자체가 잘 겹치지 않는 대신 **어느 자리의 어느 글자인지가 주장의 전부**라,
자리 표기 + 글자를 앵커로 삼는 편이 정확하다.

### 11-2. 실측 (같은 명식 3건)

| | v3 | v4 |
|---|---|---|
| 투간 주장 / 일치 | 대조 없음 | **4 / 4** |
| 통근 주장 / 일치 | 대조 없음 | **14 / 14** |
| 관계 주장 / 일치 | 8 / 8 | **7 / 7** |
| 기둥·수치 위반 | 대조 없음 | **0** |
| 근거 붙은 문장 | 79% | **89%** |
| 문장 결함 | 1종(거짓 양성) | **0** |
| 1명 원가 | 6,644 | **7,123** |

### 11-3. ⚠ 기계를 통과한 뒤에도 사람이 3건을 찾았다

전문은 `docs/FAMOUS_SAMPLE_OUTPUT_V4.md` §5. 원인은 하나다 — 검사기가 **서술형 어휘**로 주장을
식별하는데 모델이 같은 사실을 **다른 말**로 쓴다("투간되어" 대신 "드러남", "일간 정 통근" 대신
"년·월·시·일에 통근 O").

**다음 지렛대**: 검사기 어휘를 넓히는 것보다 **프롬프트가 자리+글자를 강제하게** 하는 쪽이 낫다.
관계가 7/7 인 이유가 정확히 그것이다(참여 글자를 강제했다).

### 11-4. 검사기 거짓 양성 — 누적 18건

v2 5 · v3 4 · **v4 9**. 전부 정상 본문을 거절했다. 대표:

- `일간을` 이 "일간 + 을(乙)" 로 파싱됐다 — 을은 목의 천간이면서 목적격 조사다
- 레포의 통근버스 좁힘이 `통근하여` 같은 명리 동사형까지 막았다
- 한 문장 뒤쪽의 `통근 X` 가 앞쪽 짝의 극성까지 뒤집었다
- 관계 이름 스트리퍼가 `정(丁)` 같은 **글자+한자 병기**까지 지웠다

> **검사기를 세게 만들수록 정상 본문을 거절할 위험이 함께 커진다.**

실측 본문 **12건**(v1~v4 각 3건)을 회귀로 박아 둔 이유다.

### 11-5. 6칸 명식

v3 에서 시각 미상 명식의 근거 비율이 69% 로 가장 낮았다. 원인은 둘 다였다 — 근거가 적고,
**프롬프트가 "짧아도 된다" 고 말하지 않았다.** 섹션당 4~6문장을 요구하니 빈칸을 메우려 했다.

"분량을 억지로 채우지 말라 · 3~4문장이면 충분하다 · 근거가 적을 때 할 일은 채우는 것이 아니라
여기까지만 말할 수 있다고 밝히는 것" 을 넣었다. 결과 **69% → 90%**, 길이 2,040 → 1,874자.
다만 사실 오류는 1건 남았다 — 분량 압박은 줄었지만 어휘 문제는 그대로다.

## 12. 자리+글자 강제 V5 (2026-09-05)

v4 는 대조를 켰는데도 사람이 사실 오류 3건을 찾았다. 원인은 하나였다 —
**검사기가 서술형 어휘로 주장을 식별하는데 모델이 같은 사실을 다른 말로 썼다.**

### 12-1. 관계가 왜 혼자 성공했나

v3 부터 관계만 8/8 이었다. 프롬프트를 열어 보니 관계에만 있는 것이 넷이었다.

| 관계에 있던 것 | 투간·통근에 |
|---|---|
| 전용 절(③-2) | 없음 |
| 강제문 + 대비("충이 있습니다" 가 아니라 "년지 오와 월지 자의 충(沖)") | 없음 |
| 형식 고정 — **검사기의 앵커와 같은 모양** | 없음 |
| 좋은 예/나쁜 예를 실제 문장으로 | 좋은 예가 **전부 근거 괄호 안에만** 있었다 |

⚠ **네 번째가 핵심이었다.** 프롬프트의 통근·투간 예시는 모두
`(근거: 일지 축의 지장간 신이 월간으로 투간)` 형태였다. 모델은 정확히 그것을 배웠다 —
**괄호에는 자리와 글자를 넣고 본문은 뭉뚱그리는 것**을. v4 오류 3건이 전부 그 모양이다.

### 12-2. 실측 (같은 명식 3건)

| | v4 | v5 |
|---|---|---|
| **판정된 통근 주장** | 14건 | **33건** |
| 통근 일치 | 14/14 | **33/33** |
| 투간 주장 / 일치 | 4 / 4 | **7 / 7** |
| 관계 일치 | 7/7 | **8/8** |
| **사람 대조 사실 오류** | **3건** | **0건** |
| 근거 붙은 문장 | 87% | 73% (의도한 하락) |
| 괄호 풀이된 용어 | 7종 | **12종** |
| 1명 원가 | 7,123 | **9,290** |

**대조 건수가 2.4배로 는 것이 이 트랙의 전부다.** 뭉뚱그린 문장은 애초에 주장으로 세어지지
않았고, 오류 3건이 정확히 그 세어지지 않은 자리에 있었다.

### 12-3. 딱딱해지는 것을 어떻게 막았나

1차 실측에서 **v1 의 실패가 그대로 재현됐다** — "OO지의 지장간 X가 OO간으로 투간되었습니다" 가
줄줄이 서고, 근거 괄호가 같은 말을 한 번 더 적었다. 세 줄을 더 넣어 되돌렸다:

- 자리+글자를 이미 말한 문장에는 **근거 괄호를 붙이지 말 것**
- 같은 서술어를 한 섹션에서 세 번 넘게 쓰지 말 것 — 여러 자리는 한 문장으로 묶을 것
- **형식이 고정되는 것은 자리+글자이지 문장 구조가 아니다**

결과 길이가 오히려 줄었다(2,504 → 2,069자 · 2,618 → 2,071자).

### 12-4. 섹션 간 자기모순 검사 — **필요가 없어졌다**

두 주장 모두 자리+글자를 대야 하고, 대는 순간 각각 스냅샷과 대조된다. 진짜 모순이면
둘 중 하나는 사실이 아니므로 **개별 대조에서 걸린다.** v4 의 모순이 살아남은 이유가 정확히
그 반대였다 — 둘 다 자리를 안 대서 **둘 다 판정 대상이 아니었다.**

### 12-5. ⚠ 남은 것은 종류가 다르다

`일지 사의 여기인 무가 상관으로 들어 있어 일지의 주된 십성은 상관입니다` —
자리도 글자도 맞는데 **여기(餘氣)를 주된 것이라 판정했다.** 스냅샷은 등급을 매기지 않는다.
**자료에 없는 등급 판단**이라 이번 강제로는 막지 못하고, 검사기도 보지 않는다. 다음 지렛대다.

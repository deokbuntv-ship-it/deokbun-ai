## 2. 선정 근거

목표는 "작지만 84문항의 실패 모드를 대표하는 표본"이다. 점수순 상위 25건이나 무작위 25건이 아니라,
**층(stratum) 우선 그리디**로 골랐다.

**규칙**
1. 6개 축(질문 의도 · Cross resolution kind · material contributor 수 · 점수 밴드 · PUV · 도메인)의
   **모든 값을 최소 1건씩** 덮는다. 아직 안 덮인 층을 들고 오는 케이스를 우선 뽑되, **희소한 층일수록
   가중치를 크게**(1/빈도) 준다 — 21건짜리 흔한 층보다 1건짜리 희귀 층을 먼저 확보해야 하기 때문이다.
2. 쏠림 상한: 피험자당 **≤3**, 도메인당 **≤4**.
3. 점수 밴드는 하드코딩하지 않고 **V8 delivered 분포의 3분위**로 계산한다 → 하 ≤ 56 < 중 ≤ 62 < 상.
4. 동점은 `case_id` 사전순으로 갈라 결정론을 보장한다.

**결과 — 6개 축 전부 100% 커버 (미포함 0)**

| 축 | 커버 |
|---|---|
| 질문 의도 | CAUSE_WHY · DECISION · DESCRIPTIVE · OUTCOME · PROBABILITY · TIMING (6/6) |
| resolution kind | AGREED · COMPOUND_MIXED · NON_DIRECTIONAL · NO_APPLICABLE_JUDGMENT · OUTCOME_SPLIT · QUALIFIED · SINGLE_AUTHORITY · TEMPORAL_SPLIT · TRUE_STANDOFF (9/9) |
| material contributor | 1개(4) · 2개(11) · 3개(10) |
| 점수 밴드 | 하 9 · 중 7 · 상 9 |
| PUV | YES 20 · BORDERLINE 4 · **NO 1** |
| 도메인 | 7/7 (2~4건씩) |
| 피험자 | 11명에 1~3건씩 (SUBJ-10 은 전건 거절이라 delivered 에 없음) |

**대표성 검증**: 미니팩 25건의 V8 평균은 **58.24**, V8 전체 delivered 77건 평균은 **58.36**.
0.12 차이다. 우연이 아니라 밴드를 분포에서 뽑았기 때문이다.

PUV=NO 1건과 BORDERLINE 4건을 일부러 넣었다 — 회귀가 먼저 드러나는 곳은 이미 아슬아슬한 케이스다.

## 3. 채점 — 새 rubric 을 만들지 않았다는 증명

`.runtime/minipack_score.mjs` 는 `v8_compare_score.mjs` 의 `score()` **그 자체**를 실행한다.
복사해 옮겨 적지 않았고, import 하려고 그 파일을 고치지도 않았다(`.runtime/` 은 보호 디렉터리다).
원본 소스에서 `const JARGON` ~ `// ── ONE PASS` 구간만 잘라 그대로 평가한다.

- rubric = **FINAL_BLIND_84_100PT_V1**. 가중치·밴드·PUV 규칙 전부 동일.
- 원본 SHA `43c9c001e8a60473…` 를 매 실행 대조한다. 채점기가 바뀌면 경고하고, 그 순간 baseline 도 다시 떠야 한다.
- **자기검증**: 잘라낸 rubric 으로 V8 원본 77건을 다시 채점한 결과 원본 점수와 **불일치 0건**.

거절 인정 코드는 `GROUNDING_UNAVAILABLE` 과 `AMBIGUOUS_BOUNDARY_DATE_TIME_REQUIRED` 둘이다. 후자는
2026-09-02 절기 경계일 게이트가 같은 상황을 **더 좁은** 사유로 되돌리는 것이라, 거절이 덜 정확해진 게
아니라 더 정확해졌다. 이 목록 밖의 실패는 여전히 "잘못된 거절"로 잡힌다.

## 4. 임계값과 근거

**표본이 작다는 것이 임계값 설계의 전부다.** n=25 에서 ±2~3점 흔들림은 품질 변화가 아니라 표본 노이즈다.

V8 delivered 77건의 점수 표준편차는 **8.36**. 25표본 평균의 표준오차는 8.36/√25 ≈ **1.67**.
2×SE ≈ 3.3 을 "정상 변동"으로 보고 그 바로 위에서 잡는다.

| 항목 | 한계 | 근거 |
|---|---|---|
| 총점 평균 하락 | **3.5점** | 2×SE(3.3) + 여유. 이보다 작은 하락은 노이즈와 구별 불가 |
| PUV YES 비율 하락 | **12%p** | 25건에서 3건 = 12%p. 2건(8%p)은 노이즈, 3건부터 신호 |
| 축별 평균 하락 | **1.5점** | 최대 배점 축(personalization 20점)에서도 7.5% 하락. 5·10점 축에는 더 엄격하게 작용 |
| hard fail | **0** | 안전 — 표본 크기와 무관 |
| zero-engine 성공 과금 | **0** | 〃 |
| 안전 거절 정확도 | **3/3** | 〃 |
| 거절인데 덕 과금 | **0** | 〃 |

**비대칭이 의도적이다.** 품질 지표는 노이즈를 감안해 느슨하고, 안전 지표는 표본과 무관하게 0을 요구한다.
품질은 통계지만 "돈은 받고 답은 안 준다"는 통계가 아니다.

**한계**: 이 임계값은 **평균만** 본다. 25건 중 3건이 크게 무너지고 나머지가 조금씩 올라 평균이 유지되면
통과한다. 그래서 ±5점 이상 움직인 케이스를 개별로 출력한다 — 자동 실패 조건은 아니고, 사람이 읽는 신호다.

### ⚠ 도메인별 숫자를 판단 근거로 쓰지 말 것 (2026-09-06 추가)

게이트는 **총점 평균 · 축별 평균 · PUV YES 비율 · 안전 카운터**만 본다. **도메인별 평균은 게이트가
아니고, 되어서도 안 된다.** 설계는 처음부터 그랬지만 그 근거가 적혀 있지 않았으므로 여기 남긴다.

**실증 사례**: CTO 인수 이전 세션에서 **CAREER 도메인 평균이 두 라운드 사이 55.33 → 85 로 뛰었다.**
품질이 한 라운드에 30점 오를 리 없다. 원인은 표본 크기다.

| | 표본 | 신뢰 가능? |
|---|---|---|
| 총점 평균 | n=25 (SE ≈ 1.67) | ✅ 게이트 |
| **축별** 평균 | n=25 — **모든 케이스가 모든 축에 기여한다** | ✅ 게이트 |
| **도메인별** 평균 | **n=2~4** (도메인 7종에 25건을 나눈다) | ❌ **한두 건이 평균 전체를 끌고 간다** |

**축별과 도메인별은 같은 "별"이 아니다.** 축은 25건 전부가 점수를 보태지만, 도메인은 그 도메인에
배정된 2~4건이 전부다. 그래서 축별에는 −1.5점 한계를 걸 수 있고 도메인별에는 걸 수 없다.

**실무 규칙**: 리포트에 도메인별 숫자가 보이더라도 **"이 도메인이 나빠졌다/좋아졌다"고 말하지 말 것.**
도메인별로 판단하려면 그 도메인만으로 n≥25 를 새로 뽑아야 한다.
근거: `PROJECT_STATE.md` §7.21

## 6. 사용법

```bash
# 1. 미니팩 선정 (한 번만. 결정론적이라 다시 돌려도 같은 28건)
node .runtime/minipack_select.mjs

# 2. 실행 — staging 에 배포된 코드를 대상으로
node .runtime/minipack_run.mjs --label=<라벨>

# 3. 채점 + baseline 델타. 종료코드 0=PASS, 1=FAIL
node .runtime/minipack_score.mjs --label=<라벨>

# 4. 새 baseline 으로 봉인 (의도적으로 기준을 옮길 때만)
node .runtime/minipack_score.mjs --label=<라벨> --seal
```

`.runtime/` 는 `C:\Development\DeokbunAI-blind84-final\.runtime\` 다 (앱 repo 아님).

**해석**
- `✅ PASS` — 임계값 안. 그래도 ±5점 케이스 목록은 눈으로 볼 것.
- `❌ FAIL` — 어느 지표가 얼마나 떨어졌는지 줄마다 나온다. **먼저 재실행하라.** n=25 라 한 번의 FAIL 은
  회귀일 수도, 표본일 수도 있다. 두 번 연속 같은 축에서 FAIL 이면 회귀로 본다.
- `채점기 SHA ⚠` — 채점기가 바뀌었다. baseline 을 다시 뜨기 전까지 비교값은 무의미하다.

## 8. CI 연결에 필요한 것 (실제 설정은 만들지 않았다)

자격증명이 필요하고 오너 결정 사항이므로 GitHub Actions 워크플로는 **작성하지 않았다.** 필요한 것만 적는다.

**시크릿 (전부 오너가 넣어야 함)**
1. `SUPABASE_URL` — staging (`aephpsiurgkvqcswyeie`)
2. `SUPABASE_ANON_KEY` — staging
3. `SUPABASE_SERVICE_ROLE_KEY` — 덕 충전(`grant_duk`)과 `ai_usage_logs` 조회용
4. QA 계정 자격증명 — 현재 `.runtime/reg4_credentials.json` 로컬 파일. **레포에 없고 커밋되면 안 된다**

**러너 요건**
- Node 20+ · 네트워크(staging Supabase) · 타임아웃 **≥15분**
- 아티팩트 보존: `minipack_run_<label>.jsonl`, `minipack_scores_<label>.jsonl`, `minipack_cost_<label>.json`
- 동시 실행 금지 — 같은 QA 계정을 쓰므로 세션이 충돌한다

**결정해야 할 것**
- 트리거(권장: 수동 + 야간 1회) · 실패 시 동작(막을 것인가 알림만 할 것인가) · baseline 재봉인 승인 절차

**아직 없는 것**
- 이 워크스페이스는 git repo 가 아니다(`DeokbunAI-blind84-final`). CI 가 스크립트와 봉인 아티팩트에
  접근할 방법을 먼저 정해야 한다 — 앱 repo 로 옮길지, 별도 저장소로 만들지가 선행 결정이다.

## 0-2. M13 방식 — 그리고 **"처음부터 위조" 실측**

### 채택한 설계 (두 겹)

| 겹 | 마이그레이션 | 막는 것 |
|---|---|---|
| 1 | **16** — 공유 시점 서버 스냅샷 + 본문이 바뀌면 활성 공유 자동 해지 | 진짜 리포트를 받아 **결론만 바꿔** 공유 |
| 2 | **20** — 공유 증인: 서버가 답을 만들 때 문자열 조각의 **해시**를 남기고, 공유 스냅샷은 **증인이 있는 문장만** 담는다 | **처음부터 지어낸** 리포트를 공유 |

### ⚠ "처음부터 위조" 실측 — **16 만으로는 막히지 않았다 (긴급이었다)**

이번 묶음 시작 시점(16 적용 후) 측정:

```
공유 결과: {"title": "덕분이 공식 진단서 before",
           "summary": "처음부터 지어낸 요약 — 이 사람은 3개월 안에 반드시 성공합니다 before", …}
노출 칸: summary · keyFindings · cautions · title
```

스냅샷은 **그 시점의** 본문을 떴을 뿐이고, 그 본문은 클라이언트가 쓴 것이었다. 직전 보고서가
"천장" 으로 적어 둔 바로 그 경로다.

**20 적용 후**:

```
공유 결과: {"title": "상담 보고서", "summary": "", "keyFindings": [], "cautions": [], …}
노출 칸: 없음
```

### 왜 해시가 맞는가 — 합성기가 **추출형**이라서

리포트 합성기(`consultationReportComposer.ts`)와 표현 계층(`consultationPresentationVM.ts`)은 답의
문장을 **고르고 다듬을 뿐 바꿔 쓰지 않는다**:

```
keyFindings = stripEngineLabels(trim(coreSummary / strengths[i]))
cautions    = stripEngineLabels(trim(cautions[i]))
summary     = 저장된 요약  또는  앞 결론 k개(≤3)를 공백으로 이은 것
```

그래서 증인 쪽도 **같은 정규화**(엔진 표기 3종 제거 → 한글·영숫자만)를 거쳐 해시하면 정확히 맞는다.
계약 테스트가 앱의 `stripEngineLabels` 세 패턴과 SQL 의 세 패턴이 같은지 대조한다.

### 양방향 실측 — **정상 흐름은 하나도 잃지 않는다**

진짜 상담 1회(LLM 1콜, 사용자 A)로 만든 리포트:

| 확인 | 결과 |
|---|---|
| 핵심(keyFindings) | **4/4 남음** |
| 주의(cautions) | **3/3 남음** |
| 요약 | **남음** |
| 질문(coveredTopics) | **남음** — 응답이 질문을 되풀이해서 증인이 있다 |
| 제목 | **남음** — 증인이 있는 질문에서 파생 |
| 걸러진 것 | **0** |

**진짜 + 가짜를 섞으면**: 진짜 핵심 4/4 · 주의 3/3 은 남고, **가짜만 빠진다**(`findingsDropped 1 · cautionsDropped 1`).

> ⚠ 첫 "섞기" 측정은 0건으로 FAIL 이었다. 원인은 필터가 아니라 **테스트**였다 — 같은 대화에
> 리포트를 하나 더 INSERT 했는데 한 대화에 리포트 하나라는 규칙에 걸려 두 번째가 안 생겼다.
> 앱이 실제로 하는 방식(본문 수정 → 새 공유)으로 다시 재서 4/4 PASS.

### 증인은 **실제 상담 흐름에서** 도는가

첫 적용 뒤: 골든 미니팩 25건(28건 중 거절 3건은 과금 완료가 없다) + 양성 대조 2건 = **완료 27건 → 증인 27행 ·
누락 0.** 행당 고유 해시 254~540개, 전부 64자 hex(원문 없음).
수정 뒤(두 번째 미니팩, 새 트리거): 완료 **25건 → 증인 25행 · 누락 0** · 행당 254~544개. staging 전체 완료 750 = 증인 750.

### ⚠ 적용하면서 발견한 것 2건 — **둘 다 고쳤다**

**① 이 마이그레이션 이전의 상담으로 만든 정상 리포트가 빈 공유가 된다**

증인은 트리거가 **앞으로** 남긴다. 그 전에 한 상담에는 증인이 없다. staging 실측:

| | |
|---|---|
| 증인 없는 완료 답 | **698건 · 사용자 52명** (완료 725건 중) |
| 표본 — 증인이 전혀 없는 사용자 5명의 진짜 답 5건으로 앱과 같은 방식의 리포트를 합성 | **5건 전부 핵심 0 · 주의 0 · 요약 빠짐** |

> ⚠ 첫 표본은 **편향**이었다 — 미니팩 계정을 골랐더니 대부분 "남음" 이 나왔다. 그 계정들이 20 적용 뒤
> 같은 골든 질문을 다시 돌려 증인이 생겼고, 답의 상당 부분이 엔진이 정한 **고정 문장**이라 옛 답의 문장까지
> 덮였기 때문이다. 증인이 하나도 없는 사용자로 다시 뽑았다.

원본은 **서버가 쓴** `paid_request_idempotency.response_json` 이다. 완료 행은 재생 창(24시간)이 지나도
**지워지지 않는다**(`release_paid_request` 는 PROCESSING 만 지운다 · 재생 창은 같은 request_id 재사용에만 쓰인다).
그래서 **백필 함수** `backfill_answer_witness(n)` 을 두었다. 클라이언트가 쓴 `conversation_messages` 로는
채우지 않는다(#7 — 위조 가능).

| staging 백필 | 결과 |
|---|---|
| 실행 | 300건씩 3번 — **698 → 398 → 98 → 0** (24.4초 · 30.0초 · 10.1초) |
| 확인 (REST 로 따로) | 완료 725 · 증인 725 · **없는 것 0** |
| 같은 표본 5건 | **5건 전부 핵심·주의·요약 남음** · 섞은 가짜 한 줄은 **5건 모두 빠짐** · `generatedAt` 이 원래 답의 완료 시각 |

**② 증인 트리거가 상담 완료마다 ~0.25초를 더하고 있었다**

백필을 처음에는 마이그레이션 안의 한 문장으로 넣었다 → staging 698건에서 **statement timeout(2분)**.
원인을 재 보니 트리거가 답 하나에 하는 일이 무거웠다(서버 측 `EXPLAIN ANALYZE`, 최근 답 20건):

| 방식 | 20건 | 답 하나 |
|---|---|---|
| 조각 뽑기만 | 161ms | 8ms |
| **처음 쓴 트리거** | **5,046ms** | **252ms** |
| 조각 중복 제거 먼저 | 1,272ms | 64ms |
| **+ 표기 정규식에 `strpos` 가드 (채택)** | **652ms** | **33ms** |

답 하나에 조각 ~3,500개 중 서로 다른 것은 ~450개. 엔진 표기 정규식 세 개가 비용의 ~60% 였는데 표기를 담은
조각은 **1.6%**(2,154개 중 35개)뿐이었다. 가드는 "표기 낱말이 없으면 패턴이 맞을 수 없다" 는 것만 쓰므로
결과가 같다 — **실측으로 확인**:

| 동치 확인 | 결과 |
|---|---|
| 최근 답 20건 — 옛 함수 vs 새 방식 해시 집합 | **20/20 동일** (해시 8,158개) |
| 적용 뒤 — 이미 저장된 증인 27행 vs 새 함수로 다시 계산 | **27/27 동일** (해시 11,321개) |
| 실제 공유 경로 재측정 (A 의 진짜 리포트 → 공유 → B 가 읽음) | **6/6** — 핵심 4/4 · 주의 3/3 · 요약 · 질문·제목 남음 · 가짜 빠짐 |
| 위조 24건 재측정 | **21/24** (같음) |

→ 백필은 마이그레이션 트랜잭션 **밖**의 함수로 뺐다. `db push` 는 파일 하나의 문장을 배치 하나로 보내고, 그 배치는
암묵적 한 트랜잭션이다. 그래서 백필이 길면 앞의 `drop trigger`·`create trigger` 가 잡은 `paid_request_idempotency`
잠금(drop trigger 는 ACCESS EXCLUSIVE)이 그동안 남아 **상담 시작·완료가 멈춘다.** 패키지 ①-7 이 병합 전에 0 까지 돌린다.

### 증인 설계의 성질

| | |
|---|---|
